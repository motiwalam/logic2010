# Logic 2010: reverse-engineering workspace

This branch (`reverse-engineering`) records how the Logic 2010 source code was
recovered from the installed, obfuscated jars. The resulting clean source tree lives
on the `base-logic2010` branch (untouched) and `main` (for your own changes).

## Branches

| Branch | Contents |
|---|---|
| `reverse-engineering` | This workspace: original jars, deobfuscation mappings, tooling, verification, notes. |
| `base-logic2010` | The recovered source as an ordinary Java project, exactly equivalent to the installed program. Never modified. |
| `main` | Starts as `base-logic2010`; your own patches go here. |

## Building and running

Needs only a JDK (8 or newer; tested with 25).

```sh
./build.sh                  # -> build/logic.jar (the program) and build/loader.jar (the updater)
./run.sh [INSTALL_DIR]      # run build/logic.jar against an installation (default /data/logic2010)
```

The program is only the code. The course data comes from an installation:
- the scrambled problem, rule and message files in `Contents/Resources`
- the student's `work/` folder

`run.sh` points the program at an installation just like the official launcher does.

## Pipeline

`tools/deobfuscate.sh` regenerates `logic/src/main/java` from `original/logic.jar`. It runs these steps:

1. **`tools/remap/Remap.java`** (ASM) renames the bytecode.
   - yGuard overloaded method names, even by return type alone, which Java source can't express, and gave fields IPA-letter names.
   - Every obfuscated identifier first gets a unique placeholder:
     - classes `C_xY` (a lowercase letter is followed by `_`, `$` becomes `0`)
     - fields `f123`
     - methods `m45` (overriding methods share one id)
   - `mappings/*.mapping` then assign real names:
     ```
     class bB SymbolizationToolbar   # original class name -> new name
     m123 parseFormula               # method id -> name
     f45  currentUser                # field id -> name
     ```
   - The remapper refuses mappings that would create accidental overrides, whether between the program's own methods or with JDK methods.
2. **Vineflower 1.11.1** decompiles the remapped jar. It runs with `--verify-merges`; without it, Vineflower sometimes merged two variables into one, which silently changed behaviour.
3. **`tools/fix-params.py`** works around a Vineflower renaming bug: a parameter whose name collides with a field gets renamed at its uses but not in its declaration.
4. **`patches/logic/0001-decompiler-fixes.patch`** holds the hand fixes:
   - Compile errors: string variables the decompiler typed as `Object`, lost declarations, raw-collection casts, a duplicate parameter name.
   - Fidelity fixes found by the verifier:
     - loop counters typed `byte` that would overflow past 127, including a merge sort that would loop forever on more than 128 items
     - compound assignments, and a few boolean-return shapes, restored
   - To change the source and keep the pipeline in sync, edit `logic/src/main/java`, then run `tools/make-patch.sh patches/logic/0001-decompiler-fixes.patch`.

Running the whole pipeline reproduces the committed source byte for byte.

## Verification

```sh
tools/verify.sh
```

`tools/verify.sh` builds from source, then compares every class and method with `tools/compare/Compare.java`:
- `build/logic.jar` against the original with the mappings applied (`build/logic-remapped.jar`)
- `build/loader.jar` against `original/loader.jar`

Two checks run per method:
- **Ingredient fingerprint:** the calls, field reads and writes, types instantiated, constants, arithmetic and conversions. Known harmless compiler differences are normalised away: the receiver type javac picks, synthetic accessors, and string-concatenation lowering.
- **Dataflow fingerprint:** a symbolic abstract interpretation. It records which expressions flow into every call, field or array store, return, throw and branch, independent of how locals are allocated. This is what catches wrong-variable decompiler bugs.

Differences that were inspected and found harmless are listed, with reasons, in `tools/compare/known-differences.txt`. The current result is **EQUIVALENT** for all 529 classes of `logic.jar` and all 12 classes of `loader.jar`.

The dataflow check is a heuristic. Values carried around loops are widened, so the check is weaker there. The one decompiler bug it missed was found with the GUI smoke test. It was a merged variable in a layout manager, and `--verify-merges` fixes it.

### GUI testing

`tools/run-test.sh JAR NAME` runs a jar against a throwaway copy of the installation on a virtual X display:
- It is **offline by default**, because the copied prefs identify the real student. It blocks the network with a dead proxy; set `LOGIC_ONLINE=1` to allow network access.

`tools/smoke-test.sh JAR NAME` starts the jar, dismisses the first dialog, and saves screenshots to `scratch/`. Comparing the original with the rebuild gives pixel-identical screenshots (`compare -metric AE`).

Xvfb and xdotool were installed without root by extracting the distribution packages into `~/.local/opt/xvfb`.

### Other tools

- `tools/unscramble.py FILE`: decodes the program's scrambled data files. It is a running-key cipher with a fixed key; see ARCHITECTURE.md §3. `--scramble` does the reverse.
- `tools/fetch-tools.sh`: downloads Vineflower and ASM into `tools/`. They are not committed.

## Notes and caveats

- **Java version:** the original was compiled for Java 6. The rebuild targets Java 8 bytecode, the oldest that modern javac can emit.
- **Parser packages:** `syntax1` and `syntax2` are the two JavaCC-generated formula parsers (obfuscated packages `B` and `A`). Standard JavaCC member names were used, but `jj_3R_N` numbering follows declaration order.
- **Remaining awkwardness:**
  - Local-variable names are mechanical (`jad` style, e.g. `formulaparsenode1`, `s1`).
  - Some methods contain decompiler-shaped control flow.
  - Names for rarely used or dead code are sometimes tentative. The mapping files and module docs say where.
